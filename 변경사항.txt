① 다른 도우미 번호 실호환 (재수정)
-----------------------------------

v19.4는 "번호 허용"만 풀었고, 실제로는 그 뒤 3겹에서 죽고 있었다:
  · 위습 게이트가 32172 전용 유닛 id('810e')를 요구 — 다른 도우미 문서는
    유닛 id가 문서 생성 시각 기반이라 구조적으로 통과 불가.  → 위습을
    이름(선택위습/위습/위스프)으로 찾아 별칭 행으로 싣는다.
  · 게이트를 통과해도 앱이 id로만 병합해 화면 패가 전부 0.  → id 일치율이
    절반 미만이면 이름 정규화 2차 매핑(카탈로그 내 유일명만, 실측 301/307
    유닛 · 수량 전달 확인).  32172/34366은 아무것도 안 바뀐다.
  · 비활성 32172 탭이 활성인 다른 번호 탭을 항상 이김 + SPA 로 번호가
    바뀌면 영구 기각.  → 활성 탭 우선(boot·popup), 번호 변경 시 자동
    재고정(tabs.onUpdated).
  · "왜 안 되는지"가 아무 데도 안 남던 것 → 모든 기각 사유를 기록하고
    팝업이 단계·번호까지 표시(수신 기각 · 고정 32172 ≠ 수신 34943 등).
  · 로그에 도우미 번호가 안 남아 포렌식이 막히던 것 → helperId·adapterId
    보존.

② 블링블링 + 빈 공간 채우기

    그라데이션 밑줄(전부 CSS, 외부 요청 0).
  · 희귀→전설 카드 전면 개편: 유닛 초상화(글로우 링) · 달성률 % · 진행
    바 빛줄기 · "닫는 결손" 칩 · 재료 초상 칩 — 카드 아래 거대 여백이

  · 지금 할 일 초상화 링, 파티 칩 단계색 링.  움직임은 전부
    prefers-reduced-motion 에서 꺼진다.

③ 방향 확정 설명 (63키트 처방 데이터팩)

⑤ 확정 2상위 상시 콜아웃 (0731 로그 재발 방지)

0731 판: r31에 나미를 2상위 확정했는데 판 전체 306개 판단 중 "지금 할

⑥ 막판 랜덤 흔함 노리기 (0731 로그 재발 방지)
----------------------------------------------

0731 판: 도플 변이가 흔함 3장(버기2·상디1)까지 좁혀졌는데 엔진은
r53~58 내내 HOLD 침묵이었다.  이제 46라 이후 대기 상태에서 변화·왜곡
마무리가 "흔함만 부족"(≤6장, 진짜 차단 없음)이면 카드로 승격한다:
"버기×2·상디×1만 나오면 완성 — 라운드마다 랜덤 흔함 2장, 당장 각이
없어도 공짜 확률입니다."  표시 전용 — 점수화하지 않는다(랜덤 결과
비점수화는 사용자 고정 규칙).

⑦ 숨김 탭 근본 수정 — 이제 화면에 안 띄워도 된다
-------------------------------------------------

원인 확정(tmo.gg 실번들 분석): 도우미 페이지는 페이지 타이머로 로컬
프로그램(127.0.0.1:25625)을 폴링해 화면을 그리는데, 탭이 숨겨지면
크롬이 그 타이머를 조여 DOM 자체가 동결된다.  v19.4의 30초 알람은
낡은 DOM을 더 자주 읽었을 뿐이다.

수정: MAIN world 에서 페이지의 setInterval 을 Web Worker 스케줄러로
감싼다(워커 타이머는 스로틀 면제).  숨김 상태에서도 페이지가 계속
로컬 프로그램을 읽고, 워커 틱 신호를 받아 코치가 갓 갱신된 DOM 을
바로 스캔한다.  안전장치: 함수 콜백 + 100ms~2.5초 주기만 치환, 워커
생성 실패(사이트 개편 등) 시 아무것도 바꾸지 않고 물러난다.

정직한 한계:
  · 크롬 "메모리 절약"이 탭을 얼리면 전부 멈춘다 —
    chrome://settings/performance 에 tmo.gg 예외 등록을 안내(팝업·README).
  · 사이트 개편 시 조용히 꺼지고 30초 알람 보험으로 강등된다.  그때를
    위해 팝업에 "TMO 미니 창 분리" 버튼(작은 팝업 창을 구석에 두는
    확실한 폴백)을 추가했다.

① 사용자 루미너스 UI 이식 (보라 #9d82ff · 파랑 #61baff)
--------------------------------------------------------

  · 대시보드 재배치: 다단 컬럼 → 명시적 그리드.  1행 [지금 할 일+다음
    판단 레일 | 스펙], 2행 [희귀→전설 | 최종 파티], 3행 [남는 희귀 스트립].
  · "다음 판단" 레일: 가짜 시간순 미리보기 대신 완료 후 · 다시 계산
    트리거 · 지금 보존(희귀 홀드) 3분할.
  · 희귀→전설 카드: 보유 희귀 진행도 바(owned/short), 재료 칩, 추천 순위
    연동 정렬(추천 → 제작 가능 → 진행률 → 선위).
  · 스펙 패널: 역할 행에 진행 게이지(--metric), 생존/화력 2열 그리드.
  · 최종 파티: 후보 없을 때 9환산 유령 슬롯, 파티 칩 4개 + 나머지 요약.
  · 탑바: 아이콘 통일(새 게임·설정), 문구 간결화("선위").

① 상위 플레이북 — 전수 메모가 화면에 나온다
--------------------------------------------

업로드된 상위 전수 메모(222KB)를 카탈로그 76개 상위 전부에 매핑해
ord_upper_playbook.js 로 실었다.  항목마다 세 가지:
  · 요약(≤60자): 이 상위의 특징 한 문장.
  · 활용(≤70자): 어떻게 굴려야 하는지.
  · 페어(2~4명): 같이 쓰면 좋은 유닛.

상위가 보이는 다섯 곳에 붙는다:
  · 5번 패널 상위 후보 카드(미확정 3후보) — 컴팩트 요약+페어.
  · 확정 메인 상위 카드 — 전체(요약·활용·페어).
  · 두 번째 상위(확정 블록·후보 행) — 컴팩트.
  · 상위 저격 모달 — 요약 한 줄(고를 때 참고).
  · 유닛 상세 모달 — 전용 섹션.

변형 매핑: 조로 염왕(F90H 키트 재사용), 베가펑크 위성 4종(요크·릴리스·
아틀라스는 스킬 고유 기술 근거로 개별 작성), 마르코 폼별, 료쿠규↔아라마키
·검은수염↔티치·뱀초↔기어포스 등 별칭 교차 확인.

경계(중요): 플레이북은 표시 전용이다.  엔진·플래너·워커가 이 데이터를
게이트나 점수에 쓰기 시작하면 테스트가 잡는다 — 추천 순위는 여전히
실측 티어·현재 패 계산이 정하고, 메모는 사람이 읽는 참고다.

한 화면 계약 유지: 낮은 화면(세로 ≤1000px)에서는 요약+페어를 한 줄로
말아 1920×1080=1080px·1440×900=900px 예산을 그대로 지킨다.


② 구조 점검(v19.4 보고) 결함 일괄 수정
----------------------------------------

  · 실행 로그 저장(ord_run_log.js):
    - 가져오기 한도 5MB 가 내보내기 실측(≈4.98MB)의 99.5%였다 — 32MB.
    - IndexedDB flush 실패 시 즉시 localStorage 강등이던 것을 지수
      백오프(1초→최대 30초) 재시도로, 강등하면 언제·왜를 기록하고
      summary(flushFailureStreak·persistenceDowngrade)와 콘솔에 알린다.
    - localStorage 쿼터 초과 시 가장 오래된 판을 버리고 재시도.
    - boundedPayload 절단 우선순위를 명시(round·v15·input 이 마지막까지
      살아남는다).
  · 방향 워커(ord_direction_worker.js): 요청이 겹치면 최신 것만 계산하는
    우편함 — 밀린 요청에는 superseded 응답을 즉시 돌려준다(이전에는
    낡은 결과가 새 결과를 덮을 수 있었다).
  · 부팅(ord_boot_extension.js): storage.onChanged 리스너를 첫 스냅샷
    GET 앞으로 옮겼다 — 그 사이 도착한 갱신을 놓치는 경합 제거.
  · 코어(ord_core.js): 카탈로그+DB 병합을 dataHash 로 메모(mergedDbFor)
    — 같은 패에서 decide 재호출 2675ms→1152ms 실측.
  · 테스트 러너(tests/run_all.js): 필수 회귀 앵커를 v15~v19 로 확장,
    maxBuffer 1MB→16MB(장황한 재생 출력이 내용과 무관하게 FAIL 나던 것),
    부분 SKIP 을 전체 SKIP 과 구분 집계.
  · 패키지 검증: 수동 번들 신선도 대조에서 ord_icons.js 가 빠져 있던 것
    보완(이제 번들 스크립트 전부 바이트 대조).
  · 스토리 등급표 생성기: 출력 파일명을 스토리_등급표.md 로 고정하고
    표 제목 버전을 package.json 단일 원천으로 — v17.7/v17_12 부패 제거.
  · tools/analyze_latest_failure·replay_latest_fix: 기본 입력이 저장소
    밖 업로드 경로에 박혀 있던 것 → data/ 최신 ordlog 자동 선택.
  · README.txt: 제목의 낡은 버전 표기 제거(manifest 단일 원천).

남긴 것(설계 결정 필요, 보고서 참조): 정책 게이트 히스테리시스, 탐색
시간 예산, 티어 우선 사전식 완화(저격이 공식 우회), 1366×768 세로 초과,
v18.8 부분 진행 크레딧.

② 도우미 번호 무관 인식
------------------------

번호(32172/34366)가 네 곳에 하드코딩돼 있었다: manifest 의 host_permissions
·content_scripts 매치 8패턴, background 의 SUPPORTED_HELPER_IDS 집합,
popup 의 PATTERNS·집합, boot 의 PATTERNS·집합.  새 번호의 도우미 페이지는
콘텐츠 스크립트가 아예 주입되지 않거나 주입돼도 어댑터가 없어 침묵했다.

전부 해제했다:
  · manifest: tmo.gg(+www) 의 /build-helper/* 와일드카드 4패턴.
  · background/popup/boot: 숫자 id(1~8자리) 전부 허용.
  · content: 알려진 번호(32172 주·34366 호환)는 지정 어댑터, 그 외 숫자
    번호는 범용 어댑터(tmo-<번호>-auto)로 인식.

"이 페이지가 정말 ORD 2.305 도우미인가"는 번호가 아니라 validSnapshot 의
내용 게이트가 계속 판정한다 — 유닛 300~380종 · 수량 전량 파싱 · 신뢰도
0.72 이상.  다른 게임의 도우미는 번호가 통과해도 여기서 걸린다.  tmo.gg
밖·/build-helper/ 밖으로는 권한이 넓어지지 않았다(테스트로 고정).


③ 최소화 탭에서도 데이터 수신
------------------------------

원인: 크롬은 숨김 탭의 타이머(setTimeout/setInterval)를 조인다 — 처음엔
1초, 5분 뒤엔 분당 1회.  커넥터의 2초 폴링·400ms 안정 확인·7초 하트비트가
전부 타이머라 최소화하면 수신이 사실상 멈췄다.  메모리 절약 기능이 탭을
폐기하면 콘텐츠 스크립트가 통째로 죽는 경우도 있다.

세 겹으로 고쳤다:
  · 서비스 워커 알람(30초)이 고정된 소스 탭에 ORD_BACKGROUND_TICK 메시지를
    보낸다 — 메시지 핸들러 실행은 타이머와 달리 조여지지 않으므로 즉시
    스캔·발행한다.  탭이 보일 때는 기존 2초 폴링이 그대로라 이 알람은
    사실상 숨김 탭 전용 보험이다.
  · 숨김 상태에서는 400ms 안정 확인을 생략하고 즉시 발행한다 — 숨김
    중에는 사용자 입력 churn 이 없고, 찢긴 스냅샷은 다음 스캔이 교정한다.
    숨김↔표시 전환 시에도 즉시 재스캔한다.
  · 소스 탭을 고정할 때 autoDiscardable:false 로 자동 폐기를 막는다.

한계(정직하게): 최소화 상태의 수신 주기는 최대 ~30초다(알람 하한).  또
TMO 페이지 자신이 숨김 상태에서 자기 화면 갱신을 멈추는 부분이 있다면
(그쪽 타이머도 같은 스로틀을 받는다) 코치는 그 페이지가 마지막으로 그린
패를 받는다 — 실전에서 한 판 확인이 필요하다.

앱이 죽은 게 아니었다 — 방향 후보 목록에는 조로 본인도 포함돼 있었고
언제든 한 번의 클릭으로 재확정할 수 있는 상태였다.  다만 계통을 전환했다
되돌아왔을 때 "방금 여기 있던 상위를 다시 켜시겠습니까"를 아무도 물어보지
않았다 — 처음부터 방향을 다시 비교하고 고르는 것과 똑같은 절차를
요구했다.


고친 것
-------

계통 전환이 확정 상위를 해제할 때(selectDamageMode의 conflict 분기),
해제된 상위·계통·경로·해제 시점 라운드를 releasedUpperHint 에 기억해
둔다.  그 뒤 같은 계통으로 돌아오면 1번 패널(지금 할 일) 맨 위, 방향
후보 목록보다 먼저 눈에 띄는 카드로 "OOO 확정이 계통 전환으로 방금
해제됐습니다 · 다시 확정" 버튼을 보여준다.  누르면 후보를 다시 훑을
필요 없이 그 상위로 즉시 재확정된다(captureUpperCommitment 경로 —
처음 확정했을 때와 같은 가변 보조 계산으로 이어진다).

힌트가 아무 때나 뜨진 않는다:

  · 계통이 다르면(해제 당시와 지금이 다르면) 안 보인다.
  · 해제된 지 15라운드가 넘으면 만료된다 — 40라에 해제된 걸 90라에
    "복구"하자고 뜨면 그게 더 헷갈린다.
  · 새 상위를 확정하거나(choose-direction·confirm-upper) 방향을
    초기화하거나(reset-route) 명시적으로 보류하면(hold-direction)
    힌트는 즉시 지워진다 — 이미 해결된 힌트가 나중에 다시 뜨지 않는다.

③ 재료 이름이 옆 카드를 덮던 CSS 결함

③ 물딜 2상위
------------

게임 규칙은 상위 2기 보유까지 허용한다(ord_core: '상위 2개 보유로 추가 상위
제외').  물딜 상한 1은 규칙이 아니라 플래너가 걸어 둔 전략 제약이었다.

그런데 상한만 2로 열면 두 가지가 동시에 틀린다.

  · 아무 일도 일어나지 않는다.  요구표의 main 목표가 1로 이미 충족돼 있으면
    탐색이 상위 한 기(전설 환산 3)를 더 넣을 이유가 없다.
  · 상한만 열고 요구를 안 바꾸면 9환산 계약이 깨진다.  보드 목표가
    routeBoardTarget = 9환산 - 상위×2 로 계산되므로, 기회주의적으로 상위를
    하나 더 집으면 보드 7기 + 상위 2기 = 11환산이 된다.  v19 첫 시도에서
    회귀 4건이 정확히 여기서 터졌다.

그래서 물딜 2상위는 "두 번째 상위를 확정했을 때"만 열린다.  확정하면
    · 요구표 main 목표 1 → 2 (라벨도 '상위 딜러 2')
    · 보드 목표 7기 → 5기 (상위 2기 + 보드 3기 = 9환산)
    · 상위 상한 1 → 2
가 함께 움직인다.  마딜 dual 은 원래 2상위 경로라 그대로다.  마딜 단끝은
단·끝 3기를 위한 자리가 필요해 확정을 세지 않는다 — 2상위로 가려면 마딜
2상위 경로를 고르는 것이 맞다.

실측: 흔함 400장·위습 600·료쿠규 보유 물딜 판에서
    확정 없음 → 료쿠규 1기 + 보드 6기 = 9환산
    흰수염 확정 → 료쿠규 + 흰수염 2기 + 보드 3기 = 9환산

주의(알려진 부작용): 지금 패로 도달할 수 없는 상위를 확정하면 보드 목표는
5기로 줄어드는데 두 번째 상위 자리가 비어 7환산에 머문다.  요구표의
'상위 딜러 2'가 열린 채로 남으니 코치는 그 상위를 향해 일한다 — 마음이
바뀌면 해제 버튼을 쓰면 된다.


① 두 번째 상위 관성
-------------------

v18.2가 행동 추천에 넣은 관성과 같은 취지다.  직전 계산에서 계획했던 상위를
기억해(앱: rememberPlannedUppers → settings.stickyUpperIds) 다음 계산의
타이브레이크로만 쓴다.

비교 순서가 이 기능의 전부다.  관성은

  결손을 닫는가(closed) → 건드리는가(covered) → 제어 과잉(controlPenalty)
  → [관성] → 패 소모(tierBurn) → 위습 비용

사이에 들어간다.  필수 역할을 더 닫는 후보가 나타나면 그 즉시 바뀌고,
"조금 더 싸다"로는 바뀌지 않는다.  상위 하나를 만드는 데 걸리는 라운드는
위습 몇 개보다 비싸다.  관성은 상위에만 붙는다 — 보조 전설급까지 붙이면
파티 전체가 얼어붙는다.  확정·고정된 상위는 관성 대상에서 빠진다(중복).

빔 탐색에도 같은 타이브레이크를 넣었다(nodeCompare, blueprintMatched 다음).
점수에는 넣지 않았다 — 점수 가산은 게이트처럼 작동해서 관성이 역할 판정을
이길 수 있다.


④ 제어 전담 상위 억제
---------------------

두 가지를 고쳤다.

(가) 제어 과잉 면제에서 'main' 과 'magicSupport' 를 뺀다.

hasNonControlRole 은 "이 유닛이 제어 말고 다른 것도 들고 오는가"를 보고,
그렇다면 넘치는 스턴·이감을 부수효과로 싸게 친다.  그 목록에 main 과
magicSupport 가 들어 있었다.

  · main 은 "이 유닛이 상위다"라는 부기일 뿐 화력 기여가 아니다.  이것이
    남아 있으면 모든 상위가 무조건 면제를 받는다.
  · magicSupport(마방깎·마뎀증·폭뎀증)는 증폭이라 증폭할 딜이 없으면
    화력이 아니다.

실측: 790H (C)아오키지 초월 = 스턴 1.24 · 이감 70 · 단일/끝딜/보조딜 0 ·
magicSupport 10.  기존 목록에서는 main=1·magicSupport=10 때문에 면제를 받아
이감 초과분이 ×0.9 로 계산됐다.  이제 ×4 다(같은 벡터에 끝딜 한 줄만 얹어
면제를 뒤집으면 70×3.1 = 217 만큼 차이 난다).  0730 판의 "이감이 너무
오버되서 잡힌게 좀 아쉽네"와 같은 뿌리다.

대조군: I90H (B)브룩 초월은 끝딜 1.5 를 들고 오므로 여전히 면제 대상이다.

(나) 손패의 보조가 혼자 닫을 수 있는 제어 줄은 상위 후보의 역할 크레딧에서
     빼고 센다.

아오키지 초월이 추천된 기계적 이유는 closed=2 였다.  제어 두 줄을 혼자
닫으니 최상위 비교항에서 이겼고, 그 뒤의 모든 항(제어 과잉·패 소모)은 아예
읽히지 않았다.  그런데 그때 사용자 패에는 라분(0.8스턴)과 헨콕(0.9스턴)이
있었다 — 스턴은 보조로 이미 닫히는 줄이었고, 여러 라운드가 걸리는 상위
자리를 그 줄에 쓰는 것은 낭비였다.

그래서 매 슬롯마다 "안 막힌 비상위 후보가 혼자 닫을 수 있는 제어 줄"을 먼저
모으고, 상위 후보의 closed·covered 에서 그 줄들을 제외한다.  보조가 못 닫는
줄에 대해서는 상위가 크레딧을 그대로 받는다.

근사라는 점을 적어 둔다.  안 막힘(blocked) 판정은 라운드 시작 패 기준이다.
방향은 안전하다 — 상위의 제어 크레딧만 깎으므로, 근사가 틀리면 보조가 먼저
시도되고 실패하면 다음 후보로 흘러간다.


하지 않은 것: 딜 기반 2상위 배제
--------------------------------

"딜이 안나와"를 데이터로 옮기려 했지만 근거가 반대로 나왔다.

v18.9.0 — 이감이 채워지면 1.5스턴을 놓아준다
============================================

사용자 교정(0730 마딜 2상위 클리어 판): "이감이 빡이면 스턴을 굳이 1.5로 안

무엇이 문제였나
---------------

엔진이 1.5스턴을 우솝(0.2스턴)으로 채우려 했다.  사용자는 그 자리에 도플
변화·카쿠 변화를 강제로 만들어 넣었다 — 스턴 숫자를 채우는 것보다 딜러가

1.5스턴 1.37 부족 0.13 이었다.

고친 것
-------

이감이 목표를 채우면 1.5스턴을 필수에서 권장으로 내린다.  물딜·마딜(2상위·
단끝) 세 경로 모두 같다.

  이감 충족 → stunFull required:false, recommended:true, relaxedBySlow:true
  이감 미달 → stunFull 필수 유지(생존 축 둘이 동시에 비지 않게)

0.5스턴 최소선은 어느 경우에도 필수다.

v17.7 계약을 덮는다는 점을 적어 둔다.  v17.7 은 실전 6판 재생으로 물딜
1.5스턴을 필수 하드 게이트로 세웠다.  이제 그 게이트는 "이감이 미달인 동안"만
필수다 — 근거는 사용자 플레이 판단이며, 이감이라는 다른 생존 축이 이미
닫혀 있을 때만 풀린다.

효과 실측
---------

squad_planner 균형 테스트에서 계획이 1.5스턴을 포기하고(0.934) 그 자리를
다른 데 쓰는 것이 확인됐다.  0.5 최소선과 과잉 적립 상한은 계속 검사한다 —
"스턴을 버려도 된다"가 아니라 "이감이 있으면 1.5까지 억지로 채우지 않는다"가
계약이다.

미리보기 설계도가 invalid → adapted 로 올라간 것도 이 변경의 결과다.  역할표
미완성 패가 파티를 잠그던 안전장치가 풀린 게 아니라, 완성 기준이 바뀌어 그
계획이 실제로 필수 역할을 다 채운 것이다(kept 가 아닌 adapted 는 유지).

v18.7.0 — 스펙 표기 통일
========================

전(前) — 같은 종류의 정보를 네 가지 형식으로
--------------------------------------------

  축 카드 3개   "1개 미달" + "88% · 이감 102% 35/102"
  이감 전용 핀  "현재 35 / 목표 102" + 부족 배지
  요약 3칸      맨숫자 8/9 · 3 · 5
  결손 카드     "0 / 2" + "부족 2"

이감은 축 카드와 핀에 두 번 나왔고, 축 단위("2개 미달")와 항목 단위
("단일딜 환산 2")가 한 화면에 섞였다.  숫자 위치도 형식마다 달라서 눈이
값을 찾아다녀야 했다.

후(後) — 한 가지 행 형식
------------------------

  [아이콘] 역할명 ......... 현재 / 목표 ......... 부족 N

네 칸 위치가 모든 행에서 같고 숫자는 자릿수 정렬이다.  축(생존/화력)은
행 형식을 바꾸는 대신 묶음 제목으로만 남는다 — v18 이 축을 나눈 이유
(생존은 뚫리면 그 라운드에 죽고, 화력은 밀릴 뿐)는 그대로 지킨다.
충족된 역할도 같은 형식으로 함께 보여 구조가 어디까지 닫혔는지 읽힌다.

-----------

않도록 이감은 충족이든 계산 대기든 항상 한 줄을 차지한다.  요구 목록이 비어

v18.6.0 — 6패널을 한 화면에
===========================

무엇이 틀렸나

v18.4 는 목업의 2열 배치를 그대로 옮겼는데, 목업은 이상적인 내용물로 그린

고친 것
-------

1. 다단(multicol) 3열.  브라우저가 높이를 맞춘다.  손으로 나누지 않으므로
   상태가 바뀌어도 한쪽만 길어지지 않는다.  1240px 아래는 2열, 모바일 1열.

2. 6패널 반복 비용 정리.  4패널 시절 치수가 6번 곱해지고 있었다 —
   패널 여백 16px, 헤더(34px 배지 + 22px 제목 + 14px 여백), 하단 36px.
   헤더만 360px 였다.  배지 26px · 제목 18px · 여백 10px 로 줄였다.

3. 세로 짧은 화면(≤1000px) 압축.  숨기는 것은 전부 다른 곳에 있는 정보다:
   1번 카드의 팩트 4칸(국면·다음 보스·리롤·선위)은 상태바에 있고, 4번의
   요약 3칸(환산·남은 결손·확보 조건)은 바로 위 축 카드에 있다.

결과 (같은 픽스처)
------------------

  1920×1080  문서 1,252 → 1,080   한 화면
  1600×1080  문서 1,252 → 1,080   한 화면
  1440× 900  문서 1,252 →   900   한 화면
  1366× 768  문서 1,144 →   932   여전히 164px 스크롤(밀도상 불가피)

-----------

ui_smoke 는 "그리드가 뷰포트의 80% 이상을 채울 것"을 요구했다.  4패널 시절

v18.4.0 — 늦게 나오는 상위와 6패널 화면
=======================================

사용자 지적 두 가지를 반영했다.  "50라 안에 못 만드는 상위는 고려해야
하지 않나"와 "화면을 이 목업처럼".

① 도달 라운드 — 근거 없던 나눗셈 교정
--------------------------------------

v17.3 이 넣은 도달 시점 할인은 부족 선위를 4로 나눴다(라운드당 4개 해소
가정).  커밋에 근거가 없고, 코어의 실측 상수로 만들 수 있는 가장 낙관적인
값보다도 크다:

  선택위습 0.5/라(3판 로그 측정) — 어떤 최하위 재료든 대체
  랜덤 위습 2/라               — 흔함만, 특정 1종은 2/9.  안흔함 이상은
                                랜덤으로 오지 않고 조합으로만 채운다.

그래서 해소율은 0.5(전부 안흔함+ 부족) ~ 2.5(전부 흔함 부족) 사이다.
할인은 벌점이므로 낙관 상한 2.5 로 잰다 — 가장 좋은 경우에도 마감을 넘길
때만 깎는다.  비관 하한은 화면에 범위로 함께 적는다.

  부족 61선위 @26라  ETA 42(할인 없음) → ETA 51~148(할인 0.6)
  부족 20선위 @42라  ETA 47(할인 없음) → ETA 50~ 82(할인 0.6)

첫 시도에서 선택위습만으로(0.5) 계산했다가 순위가 과하게 흔들려 테스트
3개가 깨졌다.  랜덤 위습이 흔함을 채운다는 걸 빠뜨린 것이라 상한으로
고쳤다.  하드 제외는 하지 않는다 — 0.5 든 2.5 든 3판 로그 추정치라
추정으로 후보를 지우지 않는다는 원칙은 그대로다.

② 화면 — 4패널에서 6패널로
---------------------------

v17.24 는 화면을 4칸으로 줄여 잡동사니를 없앴다.  그때 "희귀 판단" 한 칸에
두 가지(만들 수 있는 전설급 / 최종 파티에 안 쓰는 희귀)가 뭉쳐 있었는데
사용자 목업이 이 둘을 갈랐고, "다음에 뭘 하지"를 1번 카드 안에서 빼내
2번 패널로 세웠다.

  왼쪽  1 지금 할 일 · 2 할 일 미리보기 · 3 만들 수 있는 전설급
  오른쪽 4 현재 스펙 · 5 최종 파티 구성 · 6 필요없는 희귀함

데이터는 새로 만들지 않았다.  전부 엔진이 이미 내던 값이고 배열과 표시만
바꿨다.  1번 카드와 2번 패널이 같은 후속 후보 목록을 보도록
v153NextCandidateRows 로 묶었다(따로 계산하면 두 곳이 어긋난다).

시각 요소는 인라인 SVG 12종이다 — MV3 CSP 에서 외부 아이콘 폰트·이미지를
못 쓴다.  5번 패널에 9환산 진행(8/9 확보)과 자리별 단계 배지(보유·지금·
다음·예정·미정)를 넣었고, 1번 카드의 델타를 알약 한 줄에서 아이콘+
before→after 타일로 키웠다.

처음엔 span 자동 배치로 짰다가 1번 패널이 길어지면 오른쪽 열이 통째로
비는 걸 발견해 좌우를 명시적 열로 감쌌다(그리드 1155 → 868px).  5번의
보조 후보 목록은 목업에 없어 접었다 — 좌우 높이도 이걸로 맞는다.

목업에 없는 것도 버리지 않았다.  희귀 사용·보류 장부는 6번 패널 안에
접어서 유지한다(판단 근거라 사라지면 안 된다).

UI 계약 테스트 4개를 갱신했다.  "상시 노출은 4개뿐"은 v17.24 의 의도적
계약이라 바꾼 이유를 주석으로 남겼고, 계약이 지키던 문구 중 개편에서
떨어뜨린 것(상위 올리기 전 안전 리롤)은 되살렸다.

1. 표본 크기 불변성.  기존 공식은 원시 판수를 로그로 먹어서, 표본을
   12,035 → 96,627판으로 늘리면 코드 한 줄 안 고쳐도 모든 동반 가중치가

2. 플래너 정렬을 조건부 확률로.  전체 픽률은 더하지 않고 "동반 기록이
   없는 보조끼리만 줄 세우는" 대체값으로 내렸다(더하면 -0.66p).

3. 표본 교체.  불변성이 생겼으므로 전수로 바꿨다.  UI 라벨도 '상위권

   보인다.  순위는 점추정을 쓴다(Wilson 하한은 44.67%로 이득 없음).

5. 노후 경보.  6→7월 픽률이 평균 0.24%p 움직였다(최다: 에넬 +3.3p).

   3개월을 넘기면 근거 스트립이 주의색으로 재수집을 권고한다.

6. 릴리스 잡일 제거.  수동판 파일명·버전 마커·낡은 번들 청소 목록을

7. ui_smoke_test: playwright 미설치 시 FAIL 대신 SKIP.  환경 미비가

v18.2.0 — 추천 흔들림
=====================

v18.1의 읽기 누락을 고친 뒤 남은 부분을 실측했다.  실전 7판 재생 기준,
직전 추천을 만들지 않았는데 대상이 바뀐 경우 79건.  그런데 이걸 그대로
"흔들림"이라고 부르면 틀린다 — 35건은 그 사이 직전 대상이 **제작 불가**로
바뀐 것이라 다시 계획하는 게 맞다(사용자가 다른 걸 만들어 재료가 빠진
경우).  나머지 **44건**이 "여전히 만들 수 있는데 다른 걸로 바뀐" 진짜
흔들림이다.

세 가지로 나눠 다뤘다.

① 타이브레이크로는 뒤집지 않는다
--------------------------------

순위 벡터는 앞부분(회귀 · 체크포인트 · 막다른길 · 역할 전체)이 "무엇을
닫는가"를 정하고, 뒷부분(예비 선위 · 전투력 · 커버리지 · 등급 소모)은
앞이 전부 같을 때만 도는 타이브레이크다.  앞부분이 동점이면 직전 추천을
유지한다 — 선위 0.5가 늘었다는 이유로 결정이 뒤집히면 안 된다.
마진을 임의로 정하지 않아도 되도록 벡터 구조 자체를 기준으로 삼았다.

② 열등하지 않으면 바꾸지 않는다
-------------------------------

어느 필수 역할에서도 뒤지지 않고 회귀도 크지 않고 더 비싸지도 않으면
바꿀 이유가 없다.  실측 근거(20260728_170254 r48): 코치가 r45~r47 내내
흰수염을 추천하다가 r48에 봉쿠레로 갈아탔는데, 흰수염은 그 라운드에도
선위 3에 방깎 +15 · 이감 +26.5를 닫을 수 있었고 봉쿠레는 선위 5에
방깎 +11 · 1.5스턴 +0.36이었다.  실제로 r49에 다시 흰수염으로 돌아왔다.

①②는 어떤 조건에서도 "더 나쁜 것을 유지"하지 않는다.  더 나은 후보가
실제로 나타나면 그 즉시 바뀐다.  관성이 나쁜 추천을 붙잡는 것이 이
장치의 유일한 위험이라 테스트로 직접 막았다.

③ 그래도 바뀌면 계속해도 되는지 말한다
--------------------------------------

남는 것은 서로 다른 역할을 닫는 진짜 교환이다(흰수염은 이감, 봉쿠레는
스턴).  이때는 엔진 판단을 덮어쓰지 않는다 — 대신 직전 대상이 아직
유효하면 "진행 중이던 것 · 지금 순위 1위는 아니지만 이감을 여전히
닫습니다 — 만들던 것을 그대로 끝내도 손해가 아닙니다"를 카드에 남긴다.
사용자가 겪는 문제는 순위 변동 자체가 아니라 만들던 걸 버려야 하는지
모르는 것이다.

곁들여 고친 것: 직전 대상이 후보 목록에서 조용히 사라지는 문제.  관성을
넣고 처음 측정했을 때 흔들림 79건 중 직전 대상이 이번 라운드 경로에
남아 있던 것이 8건(10%)뿐이었다.  순위에서 밀린 게 아니라 candidatePool과
빔이 상위 몇 개만 남기느라 후보 풀에서 빠진 것이다.  여전히 만들 수 있는
직전 대상은 후보에 다시 넣어 평가를 받게 했다(순위를 올려 주지는 않는다).

결과
----

진짜 흔들림 44건 중
  · 관성이 유지시킨 라운드      14건
  · "계속 진행해도 됨" 안내      14건
  · 나머지 16건은 직전 대상이 실제로 열등해 바꾸는 것이 맞다

승인(확정) 라운드 수는 7판 합계 207로 변동이 없고, 클리어 판의 생존축
유지 20라운드도 그대로다 — 안정화가 판단 품질을 깎지 않았다.

남은 것
-------

흔들림을 0으로 만들지는 않았고, 만들 생각도 없다.  35건은 재계획이
맞고 16건은 실제로 더 나은 후보로 가는 것이다.  다음 판에서 사용자가
여전히 "갑자기 바뀐다"고 느끼는지가 다음 판단 기준이다.


v18.1.0 — TMO 읽기 누락 보정
============================

사용자 신고 두 가지:
  ① "지금 할 일이 자꾸 바뀌어서, 만들고 있다가 갑자기 다른 걸로 바뀐다"
  ② "지금 할 일만 보고 만들었는데 50라도 못 깨고 죽었다"

v18.0.0으로 실제 플레이한 첫 로그(ORD_2305_20260728_170254, 53라 사망)를
재생해서 원인을 찾았다.  둘 다 같은 뿌리였다.

원인 — 상위가 읽기에서 스무 번 사라졌다
---------------------------------------

사용자가 27라에 고정한 상위 (S)료쿠규(LB0H)가 TMO 스냅샷에서 **스무 번**
사라졌다 되돌아왔다.  같은 스냅샷에서 다른 유닛은 하나도 바뀌지 않았고
관측 신뢰도는 0.998이었다 — 제작으로 소비된 게 아니라 그 유닛 하나만
목록에서 빠진 것이다.  소실 구간 길이는 스무 번 모두 읽기 1~3회였고
(중앙값 1) 영구 소실은 0건이었다.

한 번 빠질 때마다 역할표가 통째로 무너졌다:

  상위 1→0 · 상시 방깎 92→57 · 이감 42.5→30

판정은 그때마다 완전히 다른 판을 보고 다시 계산했다.  r45는 한 라운드
안에서 readiness가 76↔50을 네 번 오갔다.  화면의 "지금 할 일"이 만드는
도중에 바뀐 것이 ①이고, 상위가 주던 역할을 대신 메우려는 추천을 따라가느라
정작 열린 결손이 안 닫힌 것이 ②다.

생존축 readiness 실측(보정 전 → 보정 후):

  r35   50 →  29        50 →  81
  r42   56 →  29        56 →  56
  r47   78 →  51        78 →  78
  r50   82 →  55        82 →  82

보정 전에는 만들 때마다 되감겨서 끝까지 생존축을 못 닫고 53라에 죽었다.

고친 방식
---------

최종 등급 유닛(상위·전설급)이 근거 없이 사라지면 직전 값을 잠시 유지한다
(`C.stabilizeFinalUnits`).  세 가지 예외를 둔다:

- 제작이 그 유닛을 재료로 먹었으면 그대로 받아들인다(장부가 우선이다).
- 읽기 4회를 넘겨도 안 돌아오면 진짜 없어진 것으로 처리하고 알린다.
- 희귀·특별·안흔·흔함은 대상이 아니다 — 재료로 정상 소비되는 등급이라
  붙잡으면 오히려 장부가 틀어진다.

실측 로그에서 소실→복귀 20회가 0회가 됐고, 보정이 개입한 읽기는 30회다.
라이브 앱과 재생 하니스가 같은 함수를 쓰므로 회귀 게이트가 이걸 계속 잰다.

남은 것 — 추천 흔들림은 아직 다 못 고쳤다
-----------------------------------------

읽기 누락을 고쳐도 라운드 사이 추천 교체가 판당 12~15회 남아 있고,
그중 20라 이후가 6~9회다.  이건 읽기 문제가 아니라 탐색이 라운드마다
백지에서 다시 도는 구조 때문이다 — 후보 점수가 비슷하면 선위 0.5 증가
같은 작은 변화로도 순서가 뒤집힌다.  v17.22가 역할 그룹 정렬에 넣은
스왑 마진(PACE_SWAP_MARGIN)과 같은 장치가 행동 선택에는 없다.

이건 다음 판에서 사용자가 여전히 불편한지 보고 정한다.  탐색 순서에
관성을 넣으면 나쁜 추천도 같이 붙잡을 수 있어서, 흔들림이 실제로 손해를
내는지부터 확인하는 편이 낫다.

행동한다.

  판     결과      미달 역할
  0723a  패        광보잡 0/1, 이감 92.5/102, 검증단끝 2/3, 단일 1/2
  0723b  패        전부 미달
  0724   패        없음 — 전 항목 충족
  0725   패        이감 10/102, 방깎 178/190
  0728a  패        이감 95.6/117, 1.5스턴 0.51/1.5, 끝딜 0/1, 검증단끝 1/3
  0728c  클리어    검증단끝 2/3, 단일 0.5/2

클리어는 화력 요구치를 못 채우고 이겼다.  그런데 진 판 0723a는 단일 1로
클리어(0.5)보다 화력이 높았다.  승패를 가른 건 생존 역할이다 — 클리어는
이감 105/102, 1.5스턴 1.51/1.5, 0.5스턴 0.5/0.5, 광보잡 1/1 을 간신히
전부 채웠고, 진 판들은 예외 없이 이 중 하나가 뚫려 있었다.

그래서 요구치는 하나도 낮추지 않고 분류만 붙였다(ord_core.js ROLE_AXIS).
생존 축이 뚫리면 "이대로면 라인이 뚫린다", 화력 축만 열려 있으면
"생존 구조 완성 · 화력 미달"이다.

r30 이후 모든 라운드를 재생해 생존 축 통과를 센 결과:

  0728c 클리어  20라운드 통과 (최초 r49)
  0724  패       5라운드 통과 (최초 r56)
  0723a 패       0
  0723b 패       0
  0725  패       0
  0728a 패       0

통과 "시점"이 실제 차이다.  클리어는 보스 구간 진입선인 50라 전에
닫았고, 0724는 r56에 닫고 졌다.  그래서 생존 축에 50라 마감을 붙이고
마감 전 확보 여부를 별도 신호로 낸다(policy.survivalPace).  6판 중
`마감 전 확보`가 잡히는 판은 클리어한 판 하나뿐이다.

다만 0724는 두 축을 다 닫고도 졌다.  그래서 v18도 "클리어 보장"은
말하지 않는다 — 엔진이 모르는 축(실제 보스 DPS·라인 처리·컨트롤)이
실재한다는 증거가 그 판이다.

② 각 판정 해금
--------------

`좋은각·완벽각`이 실전 로그 6판 전부에서 0건이던 원인을 확정했다.
singleEnd 경로의 마감 게이트(squad_planner.checkpointRequirementKeys)가
`singleEndStable`을 요구했는데, 이 행은 core에서 `required:false`(권장)로
선언돼 있다.  권장 행이 여기서만 하드 게이트로 쓰이는 불일치였다.
클리어 보드는 생존 5행을 전부 닫고도 singleEndStable 1/3 하나 때문에
checkpointPass=false였고, 그 하나가 각 판정 전체를 잠갔다.

물딜·dual 게이트는 원래 생존 행만으로 구성돼 있었다.  singleEnd만 화력
행을 얹고 있던 것을 같은 기준으로 맞췄다.  화력은 요구치 표에 그대로
남아 화력 축으로 따로 보고된다.

결과: 6판 재생에서 `좋은각` 0건 → 9건.

③ 침묵 금지
-----------

승인(decision.action)은 "엔진이 현재 패 정확 원장으로 증명한 제작"이라는
뜻이고 그 계약은 건드리지 않았다.  대신 절대 비지 않는 두 번째 채널을
만들었다 — `coachAction` + `confidence`(확정/유력/차선/운영).

  확정  엔진이 승인한 제작. 지금 눌러도 되는 것.
  유력  계산은 끝났으나 승인 조건을 못 넘긴 것.
  차선  증명된 게 없을 때의 최선.
  운영  만들 게 남지 않은 마감 구간에서 할 일.

6판 377라운드 전부에서 코치가 말을 한다(무응답 0).  `확정`은 승인된
행동이 있을 때만 나오며 그 대응은 테스트로 못 박았다 — 침묵을 줄이려고
승인 도장을 남발하지 않았다는 것을 숫자로 지킨다.

방향 미확정 구간에도 화면을 비우지 않는다.  다만 방향을 대신 고르지는
않는다: 클리어 로그의 그 구간을 재보면 상위 3후보가 지목한 다음 제작이
매 라운드 서로 달랐다(측정 9/9 분기).  틀린 쪽 재료를 먼저 먹으면
되돌릴 수 없으므로, 후보가 갈릴 때는 그 사실을 함께 말한다.

여기서 한 번 잘못 만들었다가 고쳤다.  후보의 첫 스텝은 워커가 전체 파티
계획을 돌려 준 뒤에만 존재하는데, 없을 때 상위 유닛 자신으로 폴백하게
해 뒀다.  재생해 보니 선위 11을 들고 있는 사용자에게 선위 32짜리 상위를
r16~r23 여덟 라운드 연속 "다음 행동"으로 내밀고 있었다.  침묵을 고친 게
아니라 거짓말로 바꾼 것이다.  지금은 지금 선위로 할 수 있는 것이 없으면
제작을 지목하지 않고 "1순위는 징베(선위 32)인데 지금 11 — 21 더 필요"
라고 말한다.

그래서 감당 가능 여부가 계약이 됐다.  지목하는 목표에는 `affordable`과
`wispShort`가 붙고, 재생 게이트가 두 가지를 강제한다: `확정`으로 승인한
것은 반드시 지금 만들 수 있어야 하고, 못 만드는 목표를 지목할 때는
부족량이 반드시 함께 나와야 한다(화면에도 "선위 N 부족" 배지로 나간다).
"모으는 중"이라고 말하는 것은 정당하지만 얼마나 모자란지 없이 이름만
내미는 것은 아니다.

마감 구간의 안내도 바꿨다.  이전에는 r55~r68 열네 라운드 내내 "지금
증명되는 제작은 없습니다"만 반복하면서 도달 불가능한 목표(류마 · 조로
11장 부족, 위습 26 부족)를 회복 목표로 내놨다.  이제는 위습·부족 재료·
도달 가능 여부를 수치로 주고 배치·컨트롤로 넘긴다.

④ 국면 모델
-----------

저장소에는 국면 분류가 이미 넷 있었고(gameFlow.phase / phaseForRound /
checkpointFor / buildDecision 관문 순서) 목적함수를 가진 것은 하나도
없었다.  "마감 구간에 할 말이 없다"는 문구 부족이 아니라 국면 부재의
증상이었다.

v18은 판단마다 국면을 낸다: `개설 · 방향 · 구축 · 운영`.  진입은 라운드가
아니라 상태다 — 51라를 넘겨도 만들 게 남아 있으면 구축이다(클리어 로그의
r51~r54가 실제로 그랬다: 도플라밍고·카쿠를 계속 제작했다).

클리어 로그의 국면 전이: r1 개설 → r16 방향 → r32 구축 → r55 운영.

⑤ 실전 로그 재생 회귀 게이트
----------------------------

지금까지 회귀 검증은 로그에서 문제가 된 라운드 한둘을 뽑아 fixture로
굳히는 방식이었다.  그 방식은 이미 아는 증상만 잡는다.  "68라운드 중
47라운드 무응답" 같은 판 전체의 성질은 판을 통째로 돌려야 보인다.

`tests/lib/ordlog_replay.js` 가 로그를 라운드 단위로 복원해 살아 있는
엔진에 다시 먹인다.  `tests/v18_replay_gate_test.js` 가 6판을 전부 돌려
네 가지를 강제한다: 무응답 0, 확신 등급 누락 0, 생존 축이 승패를 설명할
것, `마감 전 확보`가 클리어 판에서만 잡힐 것.  마지막으로 클리어 판이
여전히 화력 축 미달로 끝나는지도 검사한다 — 요구치를 낮춰서 초록불을
켠 것이라면 이 테스트가 의미를 잃기 때문이다.

실행에 약 150초가 걸려 run_all.js에 파일별 예산을 뒀다.

판단 엔진 재설계
---------------

- 역할 판정 기준 전환: 필수 역할표(이감·스턴·단일 등)의 현재값을
  durable(전설급·상위만)에서 live(보유 희귀·특별의 직접 전투 역할 포함)
  기준으로 바꿨습니다. 내구성은 회귀 가드가 대신 지킵니다 — 전투 역할을
  주는 희귀를 재료로 소비하는 제작은 그 결손이 다시 열리는 것이 그대로
  보이므로 자동으로 감점·차단됩니다.
- 행동 후보 확장: 탐색 후보가 전설급+상위뿐이던 것을, 열린 필수 결손에
  기여하는 희귀함 제작까지 포함하도록 확장했습니다. 50라 재현 패에서
  페로나(이감20) 0선위, 57라 재현 패에서 아오키지(이감10)가 즉시
  제안됩니다. 구버전은 두 지점 모두 빈 HOLD였습니다.
- 상위 전략 필수 역할 편입: 메인 상위별 필수 조건(예: (D)드래곤의
  단일 2·끝딜 1)이 판정 그룹·구조 통과·탐색 점수에 반영됩니다.
  이전에는 화면에 결손으로 뜨면서도 어떤 판단에도 연결되지 않았습니다.
- 위습 예산 보호 일반화: 물딜 전용 + 40라 이후 전용이던 예산 가드를
  모든 경로(물딜·dual·singleEnd)·모든 필수 역할로 확장했습니다. 열린
  필수 결손마다 최저 선위 마감 후보를 예약하고, 그 후보를 굶기는 다른
  제작은 순위 계산 전에 제외합니다.
- 필수 보강 우선 승인: 필수 결손을 직접 줄이는 제작은 후속 경로 수
  감소를 이유로 거부하지 않습니다(회귀·개선 검증은 유지).
- 회복 사다리: 증명 가능한 제작이 없으면 결손별 최근접 후보와 부족
  재료·필요 선위를 제시합니다. 침묵하는 HOLD는 더 이상 없습니다.
  ROUTE_CHOICE(방향 선택 대기) 중에도 선두 경로 기준 참고 목표를
  보여줍니다.
- 후반 체크포인트 세분화: 51~65라 단일 구간을 55·60·65라 마감으로
  나눠 긴급도 구배를 복원했습니다.
- 판정 등급 버그 수정: evaluate의 status/label이 JS 라벨 문 버그로
  항상 undefined였던 것을 고쳤습니다(기록의 "status": "" 원인).

한 화면 UI 재설계
----------------

- 8개 영역 구성은 유지하되, 화면을 3개 밴드(실행 스트립 / 판단·스펙 /
  자원·상위)로 재배치하고 그리드가 뷰포트 높이를 채우도록 했습니다.
  1080p에서 하단 절반이 비던 문제가 사라졌습니다.
- 현재 스펙: 필수 역할마다 진행 막대를 추가하고, 상위 전략 필수
  (단일·끝딜)까지 최대 8개 행을 표시합니다.
- 다음 행동: 대안 후보를 카드 안에 인라인으로 표시하고, HOLD 시
  회복 사다리(결손별 최근접 목표·부족 재료·필요 선위)를 보여줍니다.
- 다음 행동 미리 준비: 비어 있으면 회복 목표로 채웁니다.
- 상위 정보: 확정 상위의 조합 필수 역할 충족 현황 칩을 추가했습니다.
- 판단 잠금 탈출구 복원: 새 게임 패 확인 대기의 '현재 보이는 패로
  계속'과 제작 거래 잠김의 '거래 취소' 버튼이 실행 화면에 다시
  존재합니다(이전에는 도달 불가 렌더러에만 있었습니다).
- 판단 기록 뷰어 복원: 상단 '기록' 버튼으로 진행 기록을 다시 볼 수
  있습니다.
- 포커스 보호 확대: 게임 결과 모달 입력 중 스냅샷·토스트·시계 갱신이
  입력을 끊지 않습니다.
- 최소 글자 크기와 저대비 색을 한 단계 올려 가독성을 개선했습니다.

감사 후속 수정 (전 모듈 감사 워크플로 확정 발견 반영)
------------------------------------------------

- 스냅샷 유닛 수 검증 밴드를 게임 패치 내성 있게 조정: 핵심 검증은
  로컬 카탈로그 크기에서 파생(현재 300~380과 동일)하고, 카탈로그가 없는

  아예 보지 않았기 때문이다.

변경
- ord_core: upperTierGrade(unit) 신설. 이름 접두에서 티어 문자를 읽고
  rank(S0~F5)를 낸다. 미표기 3종(요크·릴리스·아틀라스)은 서열을 알 수
  없으므로 B~C 사이 중립값 2.5 — 맨 뒤로 밀면 실측 픽이 있는 유닛이
  영구히 잠긴다.
- ord_v15_engine: clearValueCompare에 티어 낙폭을 1순위 축으로 추가.
  비교 순서는 (보상·특수재료 전제) → (티어 낙폭) → (결손 기여) →
  (나머지 가치)가 됐다. v17.19의 roleFit은 티어 내부 타이브레이크로
  내려간다 — 상위는 티어로 고르고 결손은 전설급 세트로 메운다는
  실전 구조에 맞춘 것이다.
- 티어 낙폭 = max(0, 단계차 − 선위절약/20).  기준 티어는 "50라 준비
  창 안에 도달 가능한(deadlineFactor 1) 후보 중 최고 티어"이고, 기준
  선위는 그 티어의 최저 누적 선위다.  60선위짜리 S가 기준이 되면 축이
  무력해지므로 도달 가능성을 먼저 건다.  0.5 단위로 양자화해 미세한
  선위 차이가 티어 축을 흔들지 않게 했다.
- 한 단계당 20선위는 엔진의 도달 환산(4선위/라)으로 약 5라운드치다.
  "아주 잘"에 방점이 있으므로 몇 선위 아끼는 정도로는 내려가지 않는다.
- 낙폭 계산은 레인별 숏리스트·투영 후·레인 병합 후 세 번 다시 매긴다.

  레인마다 도달 가능한 최고 티어가 다르기 때문이다.
- 화면: 후보 카드와 메인 상위 줄에 티어 배지(S~F 색 구분)를 붙이고,
  최고 티어가 아닌 후보에는 `최고 티어 −N단계`(선위로 상쇄된 경우

v17.21 추가 변경 (사용자 v17.20 리뷰 후속 — 성능·순서·미검증 DPS·보조 순위)
--------------------------------------------------------------------------

사용자가 직접 작성한 v17.20(상위 티어·각 기반 추천)을 기준으로 채택한 뒤,
리뷰에서 실측된 문제 네 가지를 고쳤다.

1. 성능 — 방향 미확정 구간 E.decide 2.8초 → 1.6~2.0초
   원인: applyBlueprintRanking이 숏리스트 8개 전부에 rankUpperBlueprints
   (후보당 ~250ms, 9환산 전체 파티 계획)를 돌렸다. 프로파일 결과 2,051ms

   바뀔 때마다 다시 걸리며, 그 구간이 정확히 25라 방향 결정 구간이다.
   조치: 숏리스트 8→6, 전체 파티 계획은 상위 3개(+승격 가능 티어 슬롯)
   까지만. 계획하지 않은 후보는 각 라벨을 지어내지 않고 '미평가'로
   명시하고 basis='route-projection-only'를 남긴다.
   남은 비용은 여전히 크다 — 근본 해결은 ord_direction_worker로 옮기는
   것이고 이번 범위 밖이다.

2. 표시 순서 — 계획 여부가 티어를 덮어쓰던 문제
   mixedPlanCompare 신설: 둘 다 계획됨이면 전체 파티 비교, 둘 다 미계획
   이면 티어 우선, 한쪽만 계획됨이면 티어를 먼저 본다. 이게 없으면
   "계획됐다"는 이유만으로 B티어가 A티어 위로 올라가는 아티팩트가 생긴다.
   레인별·병합·최종 세 곳의 정렬을 모두 이 비교자로 통일했다.

3. upperBlueprintCompare — 티어를 자원 가용성보다 앞으로
   기존 순서는 guaranteed → handFeasible → wispFeasible → safetyBand →
   티어였다. 그래서 "지금 살 수 있다"는 이유만으로 D티어가 B티어 위로
   올라왔다(전부 계획했을 때 [S][A][A][D][D][B]로 확인). 사용자가 지적한
   "가반이 좋지도 않은데 계속 올라온다"와 같은 현상이다. 티어보다 앞설 수
   있는 각은 guaranteed(완성 보장)와 angleBand 승격(effectiveTierRank)
   뿐으로 정리했다. 실전 로그 3판 27라 재생 결과가 전부 티어 단조가 됐다.

4. 각(角) 판정의 뒤집힌 조건
   upperAngleBand가 `prefixActionCount>=2`를 요구해, 이미 목표 환산을
   채워 더 만들 게 없는 보드가 오히려 미래각(0)으로 떨어졌다. "남은 행동
   수"가 아니라 "경로가 있거나 이미 도착했는가"로 바꿨다(angleHasPath).
   (조사 기록) 로그 4판에서 좋은각·완벽각은 여전히 0건인데, 그 원인은
   조건이 아니라 safePrefix.checkpointPass가 전부 false라는 것이다.
   0724(필수 결손이 처음으로 전부 닫힌 판)의 50라조차 readiness 93~98에
   checkpointPass false다 — 이감·방깎 결손이 열려 있으면 체크포인트를
   못 지나기 때문이며, 각 판정은 그걸 정직하게 보고하고 있다. 임계값을
   낮춰 각이 아닌 판을 각이라 부르지 않는다.

5. 미검증 스킬 DPS 감산 (v17.19에서 만든 것을 이식)
   skillProcTrust 신설: coverage 통계(평가비 × 1/(1+조건밀도), 하한 0.1)로
   trustedDps를 낸다. 카벤딧슈 발동 4,973,450/초 → 1,808,527/초(신뢰 36%).
   dps 필드의 기존 의미는 유지해 호출부 호환을 지켰고, clearValueScore와
   4번 패널·상위 카드 커버리지가 모두 trustedDps를 쓴다. 화면에는
   "미검증 감산" 배지와 원값→감산값을 함께 표시한다.

6. 보조 유닛 순위 (nodeRank)
   등급 소모량이 누적 선위·후속 커버리지보다 앞에 있어 "패를 더 많이
   태우는 조합"이 "더 싸고 다음 결손까지 닫는 조합"을 이겼다. 후속
   커버리지 → 선위 → 등급 소모 순으로 교정하고 story를 제거했다.

   뒤처짐"으로 바꿨다.
     behind = 요구 진척(pace) − 실제 진척(progress)
     pace     = clamp((현재라운드 − 10) / (그룹 마감 − 10), 0, 1)
     progress = 1 − (그룹 행들의 상대 결손 평균)
   그룹 마감은 역할 키에서 나온다(방깎·0.5스턴 40라, 이감·광보잡 45라,

   핵심이다 — 최악 행만 보면 미충족 이진 역할(광보잡 0/1) 하나가 그룹
   전체를 0으로 만들어 서로 다른 두 그룹이 똑같이 "진척 0"이 되고 정렬이
   정적 순서로 되돌아간다. 뒤처짐 차이가 0.08을 넘을 때만 순서를 뒤집어
   매 라운드 추천이 요동치지 않게 했다.

v17.27 추가 변경 (지금 가진 희귀함으로 만들 수 있는 전설급 — 독립 칸)
--------------------------------------------------------------------

사용자 요청: "중간에 자꾸 재료 모은다고 다음 행동 추천을 안 해주더라.
지금 가진 희귀함으로 만들 수 있는 전설급 유닛 칸을 하나 만들어줘."

문제: 재료 수집 구간에서는 다음 행동이 PREPARE로 잠기고 3번 영역의
"만들 수 있는 전설급"도 플래너 계획에 묶여 있어, 화면에 지금 할 수 있는
게 안 보인다. 사용자가 스스로 판단할 근거가 사라진다.

조치: 판단 엔진과 독립된 사실 칸을 3번 영역에 신설했다.
- ord_core.rareCraftableLegends(state,options): 보유 희귀함마다, 그
  희귀를 실제로 소모하면서 지금 만들 수 있는 전설급을 묶어 낸다.
  이미 보유한 유닛과 상위는 제외하고, 계열(물딜/마딜)이 정해졌으면
  반대 계열은 뺀다. 희귀당 최대 6종, 초과분은 "외 N종"으로 표시.
- 정렬: 바로 제작 가능 → 선위만 모자람 → 특수 선행재료로 막힘.
  각 항목에 필요 선위(또는 부족 선위·부족 재료)와 역할 요약을 붙인다.
- 이 칸은 순위나 권장이 아니라 현재 패 원장으로 계산한 사실이다 —
  PREPARE/HOLD/ROUTE_CHOICE 어느 상태에서도 동일하게 산출된다.

같이 정리한 것
- 카타쿠리(공증·체젠형) 조사: "카타쿠리는 체젠 조합인데 에이스 왜곡을
  추천한다"는 지적을 재현했다. 35·40라 추천이 블랙마리아(왜곡)
  (방깎15·체젠0·공증0)였다. 다만 원인은 추천 순서가 아니라 목표치였다 —
  upperStrategy의 needs가 `공증 30 · 체젠 1`인데 카타쿠리 자신이 체젠
  2.85를 주고 보드 공증이 이미 30이라 엔진에는 "이미 충족"으로 잡힌다
  (실측: attack 30/30, regen 2.85/1). 즉 체젠을 더 쌓아야 하는 빌드라면
  needs 목표치를 올려야 하는 문제이고, 적정치는 게임 판단이라 임의로
  정하지 않았다. 시도했던 마감 앞당김(전략 needs 40라)은 회귀 테스트를
  깨고 이 사례를 고치지도 못해 되돌렸다.

검증: npm run test:strict 98/98 (playwright UI 스모크 포함).

희귀를 실제로 쓰는 조합만 묶는지·이미 보유한 유닛 제외, 바로 제작
